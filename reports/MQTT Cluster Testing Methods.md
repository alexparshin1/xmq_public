# How to measure the scaling limit of an XMQ cluster

Similar testing systems exist, and a good methodology for XMQ can be assembled from them. **OpenMessaging Benchmark is the most useful for organizing measurements, HiveMQ Swarm for distributing MQTT clients, and RabbitMQ benchmarker for the cluster size matrix.** The published EMQX experiment demonstrates direct distribution of clients across nodes and a separate measurement of subscription creation rate. However, among the reviewed sources no ready-made suite was found that combines all five of our loads and automatically establishes after what number of nodes performance degrades. The proposed path is to keep the standard `xmq_scn` scenarios, add controlled client placement, and borrow the validity rules for measurements. A home stand will allow the methodology to be validated; AWS will be needed to investigate adding independent machines.

## Which existing tests are worth using

| Source | What was reviewed | What to carry over to XMQ |
|---|---|---|
| [OpenMessaging Benchmark](https://github.com/openmessaging/benchmark) | Separate workloads, distributed workers, MQTT 5 driver | Separation of infrastructure, load, metrics and results |
| [HiveMQ Swarm](https://docs.hivemq.com/hivemq-swarm/latest/commands.html) | Multiple brokers in the connect command, round-robin, deterministic topics | Controlled client placement and publisher/subscriber matching |
| [RabbitMQ benchmarker](https://github.com/rabbitmq/benchmarker) | Automation of cloud test stands, monitoring, cluster size/cores/disk/replication matrix | Independent resource and topology parameters, reproducible series |
| [EMQX 100M experiment](https://www.emqx.com/en/blog/reaching-100m-mqtt-connections-with-emqx-5-0) | Direct connections without a load balancer, preparing subscribers before publishing | Readiness barrier and separate assessment of subscription scaling |
| [Open MQTT Benchmark Suite](https://github.com/emqx/mqttbs) | Connections, P2P, Fan-Out, Fan-In; core cases limited to a single broker | Baseline loads and metrics, but the cluster methodology has to be completed |

OpenMessaging Benchmark is especially useful because it separates publish rate, consumption, backlog, publish latency and the lag of sending behind a given schedule. If the generator stops sustaining the required rate, that becomes a visible result. Its MQTT 5 driver is a candidate for independently validating `xmq_scn`; the existence of a driver does not yet prove compatibility with all our scenarios. The documentation and the current implementation of automatic sustainable-rate search require separate verification at a pinned commit, so this algorithm should not be relied upon in advance. ([OMB guide](https://openmessaging.cloud/docs/benchmarks/), [project code](https://github.com/openmessaging/benchmark))

RabbitMQ benchmarker is closest to the question "how many nodes is it worth adding": its configurations separate hardware resources, broker settings and topology. The RabbitMQ article separately examines the choice between several large VMs and a large number of small ones, including the effect of clients, queues and backlog. RabbitMQ's architecture differs from XMQ, but the experimental setup itself is applicable. ([Benchmarker](https://github.com/rabbitmq/benchmarker), [Cluster sizing](https://www.rabbitmq.com/blog/2020/06/18/cluster-sizing-and-other-considerations))

Among MQTT tools, `emqtt-bench` provides concrete examples of splitting client ranges between generators and using multiple outbound IPs. Its code contains payload headers with a counter and a timestamp. `emqttb` adds ramp up/down, automatic load changes and stage markers. These are useful ideas for exploratory runs, but final comparisons are better carried out with a fixed load: automatic rate reduction would otherwise hide broker overload. ([emqtt-bench](https://github.com/emqx/emqtt-bench), [payload headers in the code](https://github.com/emqx/emqtt-bench/blob/master/src/emqtt_bench.erl), [emqttb](https://github.com/emqx/emqttb))

The independent study of distributed MQTT brokers by Koziolek et al. is useful for its separation of performance, scalability and resilience, including message loss. Its historical throughput figures cannot be transferred to XMQ. Full reproducibility of the specific durations and repetitions could not be confirmed from the available materials. ([2020 study](https://www.koziolek.de/docs/Koziolek2020-ECSA-preprint.pdf))

## Client placement determines the work being measured

**Evenly distributing connections is not enough.** If a P2P publisher and the corresponding subscriber use the same `index % N` rule, all pairs will end up on the same broker. Such a distribution will load the nodes but will hardly test inter-node transfer. Swarm demonstrates a convenient way to separately specify multiple brokers and topic assignment; for XMQ these two decisions should also be separated. ([Swarm commands](https://docs.hivemq.com/hivemq-swarm/latest/commands.html))

Three reproducible P2P modes are proposed: local pairs; pairs on different nodes with an offset in assignment; independent distribution of the sides with a fixed seed. In the latter case the expected share of inter-node pairs is `1 − 1/N`: this is a mathematical consequence of independent uniform assignment, not the result of someone else's benchmark. In each run the actual placement and the number of clients per node must be recorded. Intra-host inter-process transfer and inter-host transfer must also be distinguished in the results.

For Fan-In, separate cases are needed for concentration of work on a single node and for distributing groups across nodes. A shared subscription and many publishers on a regular subscription produce different work; the original semantics of the standard scenario must be preserved. For Fan-Out, the number of deliveries per publication is fixed: changing the number of subscribers together with the number of nodes would otherwise change the load amplification. Connections is split into the number of held connections and the rate of establishing new ones; churn should be tested in a separate series. For Persistence, online transfer, accumulation of offline backlog, its draining and recovery after restart are considered separately. These are recommendations for XMQ, not ready-made requirements of a single external suite.

In the first comparison it is reasonable to connect clients directly to broker addresses, as in the EMQX experiment. The load balancer then becomes a separate factor: its distribution policy and its own limit must not silently determine the cluster curve. Global ranges of client IDs and topics between generators are mandatory, otherwise session takeover and incorrect pair matching will distort the result. ([EMQX experiment](https://www.emqx.com/en/blog/reaching-100m-mqtt-connections-with-emqx-5-0), [emqtt-bench client ranges](https://github.com/emqx/emqtt-bench))

## The limit must be sought along several curves

The phrase "performance degradation begins" allows three different outcomes: latency grows at the previous load; total capacity stops growing; total capacity itself declines. **A decline in per-node performance while total performance grows means diminishing returns, but not yet an absolute decline.** SPECjms2007 also distinguishes between growth in the number of destinations and growth in traffic with their number unchanged — identical messages/s do not make loads equivalent. SPEC was completed in 2016; here it serves as a source of methodology. ([SPEC design](https://www.spec.org/jms2007/docs/DesignDocument.html), [SPECjms2007 status](https://spec.org/jms2007/))

For XMQ three series are proposed: a constant total standard load; a load growing in proportion to the number of nodes; a search for the maximum sustainable rate `C(N)` for each size. In the latter case, sustainability means that the actual offered rate matches the specified one, expected deliveries are performed, backlog does not grow, and latencies and errors stay within pre-selected limits. The boundary is first sought in steps, then confirmed by a separate ten-minute run. A short step discovers a candidate but does not prove sustainability.

| Stage | Sizes | What is recorded | What we determine |
|---|---|---|---|
| Home baseline | 1, 2, 3 nodes on different hosts | The standard five loads | Cost of distributed work |
| Home density | 2, 4, 6 processes, two per host involved | Explicit distribution of CPU and clients | Impact of process contention |
| Capacity search | Same sizes, first P2P local/cross/mixed | Payload, QoS, topics, session policy | `C(N)` and the limiting factor |
| AWS reconnaissance | For example 3, 5, 10, 20, 35, 50 VMs | One VM type, initially one AZ | Region of saturation or decline |
| Refinement | Neighboring sizes around the inflection point | Same conditions and load | Reproducibility of the observed effect |

This is a proposed matrix, not a norm from the sources. At home it is useful first to validate the methodology on P2P, then extend it to all five standard loads. In AWS a short window is better spent on pre-selected points rather than on initial debugging. The following should be shown: `C(N)`, `C(N)/N`, efficiency `C(N)/(N·C(1))` and latencies at a fixed load. If there is no decline up to six nodes, a correct home conclusion is limited to that range.

Around the presumed inflection point, at least three independent repetitions and a return to a smaller size after a larger one are proposed. The spread should be shown, not hidden in a single average. At home, differences between the machines themselves may be stronger than differences between neighboring N: it is necessary to record which hosts were included in each point. Shared storage is part of the system under test; its saturation sets the limit of a given configuration but does not by itself prove a limit of XMQ's clustering algorithm.

## Measurement validity matters more than the maximum messages per second

Minimum reporting must distinguish specified publications, those actually sent, those acknowledged by the broker, and messages uniquely delivered to subscribers. PUBACK does not confirm completion of delivery to a subscriber. For Fan-Out, incoming publications and outgoing deliveries are counted separately; for shared subscriptions delivery to one group member is expected. Also needed are gaps, duplicates, reconnects, inflight, backlog and generator scheduler latency.

If the generator waits for a response and reduces its offered rate following server slowdown, the measured latencies of successful messages may look healthy. `wrk2` demonstrates the technique of measuring latency from the scheduled send time, and HdrHistogram allows distributions to be merged. For MQTT, both the send latency relative to the schedule and the actual offered rate should be recorded. Percentiles from different generators must not be averaged: histograms are merged. ([wrk2](https://github.com/giltene/wrk2), [HdrHistogram](https://github.com/HdrHistogram/HdrHistogram))

Temporal phases must be stored separately: configuration, connect, subscribe, subscription propagation, warm-up, measurement, bounded drain. PerfTest provides an example of synchronized start of prepared generators with a timeout. For one-way latency between machines, measured clock accuracy is required; local monotonic timestamps from different machines are not comparable. For P2P it is convenient to keep both sides of a pair on the same generator, connecting them to different brokers. ([PerfTest](https://perftest.rabbitmq.com/))

On every broker, generator and shared storage, CPU and run queues, RAM/swap, network and retransmits, disk latency and queues should be collected. The USE approach suggests looking at utilization, saturation and errors for each resource. A suspicion of a generator limit is verified by adding generators at the same total load. ([USE method](https://www.brendangregg.com/usemethod.html))

A ten-minute run characterizes short-term sustainability. For Persistence it may not cover checkpointing, cache exhaustion or backlog accumulation. SPEC separately requires steady state and verification of delivery completion, but its historical durations are not an obligation for our budget test. Long preliminary runs are better performed at home. ([SPEC run rules](https://www.spec.org/jms2007/docs/RunRules.html))

## A short AWS test requires a separate deletion deadline

OMB shows the separation of Terraform infrastructure, Ansible configuration and distributed client machines. AWS Distributed Load Testing is useful for parallel orchestration, synchronization and error handling; it does not deploy the XMQ EC2 cluster itself. These projects provide lifecycle examples, not a ready-made solution to our task. ([OMB tutorial](https://openmessaging.cloud/docs/benchmarks/kafka/), [AWS DLT architecture](https://docs.aws.amazon.com/solutions/latest/distributed-load-testing-on-aws/architecture-overview.html))

The proposed cycle: validate the manifest, set an independent deletion deadline, create and configure machines in parallel, verify membership and routes, prepare clients, perform warm-up and 600 seconds of measurement, upload data on a limited basis, delete resources and check for leftovers. A ready-made image reduces installation unpredictability. The barrier checks not only the TCP port but also binary versions, membership, storage and actual inter-node delivery.

**A local `finally` is not enough if the home controller is lost.** In AWS an independent cleanup workflow is needed, with a deadline, retries and result verification. EventBridge Scheduler provides one-time schedules, retry policy and DLQ, but a successful handler invocation does not yet mean successful deletion. A TTL tag by itself deletes nothing. EC2 termination also leaves EBS behind if DeleteOnTermination is disabled. ([Scheduler](https://docs.aws.amazon.com/scheduler/latest/UserGuide/schedule-types.html), [retry and DLQ](https://docs.aws.amazon.com/scheduler/latest/UserGuide/configuring-schedule-dlq.html), [EC2 termination](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/how-ec2-instance-termination-works.html))

For XMQ, the manifest of created resources and the `run_id` should be stored, with regular cleanup, an independent deadline and periodic checking of overdue runs. First test controller loss on two VMs. The budget includes deployment, warm-up, generators and deletion. Five consecutive ten-minute loads already require at least 50 minutes of measurement: the promise of "the whole test in ten minutes" is possible only for one selected point.

The practical next step is to describe a unified manifest of load and client placement, then validate it on the home P2P in three routing modes. This will provide a basis for refining `xmq_scn` according to specific requirements and will allow the meter to be validated with an independent MQTT client before scaling the cloud stand.
