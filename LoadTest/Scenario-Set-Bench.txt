# Scenario set: home bench (broker on thinker11, client on thinker10)
#
# What this set is for: the per-version regression record in results/versions/. One file per XMQ
# version per host, XMQ only, read against the file for the previous version on the SAME host. It
# answers one question - did this version move? - and nothing else. The numbers are not published
# and are not comparable with AWS: the bench hosts differ by more than their CPUs, and a HZ=250
# kernel is worth 65% to XMQ on its own.
#
# How to run it: one scenario at a time, in the order below, restarting the broker before each.
# A broker still holding the previous scenario's sessions is not the clean broker the record
# claims to have measured. Persistence off, in-memory storage, no Redis, unless a note says
# otherwise. Score every run by the interval median with the first and last rows dropped - never
# the run average, which the ramp-up and the tail-off drag around.
#
# Machine-readable: every line that is not a '#' comment or blank is one scenario, in run order.

# Fan-Out first: cheap, and it warms nothing the later scenarios care about.

# In the set until the drift the run shows latency climbing to ~5ms while the rate holds
# at 250k/s - is explained. Drop it once it is.
Fan-Out-5-1000-5-250K-10min.json

Fan-In-50K-500-50K-50K.json
Point-To-Point-50K-50K-50K-50K.json

# The same shape at twice the rate: 2 msg/s per publisher, 100k/s aggregate. It did not complete
# on 0.9.14 or on 0.9.15, and neither record says what "did not complete" looked like - which is
# the reason it is in the set rather than filed under known-broken. A scenario that fails here
# for an unknown reason is a scenario that can fail on AWS too, and there the answer is billed
# by the hour. Run it, and when it fails, record how: client CPU, broker CPU, and the last thing
# the run printed.
Point-To-Point-50K-50K-50K-100K.json

# The one scenario in this set run with persistence ON: clean_session false AND Redis reachable,
# XMQ persistence enabled, clean_start true against an empty database. Persistent sessions over
# in-memory storage measure session bookkeeping and nothing else - the storage they are named
# after is not in the run at all, which is what makes that version of it pointless.
#
# NOT comparable with the 0.9.14 and 0.9.15 files, which recorded this scenario with persistence
# off. The comparable series for it starts at 0.9.16.
#
# On this bench Redis runs on the broker host itself (redis_server resolves to 127.0.1.1 there),
# so it competes with the broker for the same 8 threads. Record Redis's own CPU alongside.
Point-To-Point-20K-persistent.json

# The connection scenario last. It leaves the broker holding peak RSS - which it keeps, by
# design - and that would then sit underneath every latency scenario run after it.
1M-Connections-5K-rate.json

# NOT in this set, and why:
#
# Fan-Out-5-1000-5-250K.json          Dropped 2026-09-22. It is bounded by message count, not by
#                                     time, and stops after a thousand messages: the whole run is
#                                     4-5 seconds and is ramp-up end to end. Its eight samples are
#                                     400ms apart where every other scenario's are minutes, so it
#                                     can show no drift at all. It had been kept for comparability
#                                     with the 0.9.14 and 0.9.15 records - and that is the cost of
#                                     dropping it: those two files carry a first row this set no
#                                     longer produces. Worth paying, because the row read as a
#                                     result while measuring nothing. The -10min variant above
#                                     measures the same scenario for real.
#
# 500K-Connections-2500-rate.json     Half of a run this bench can do whole. It is barely shorter
#                                     than the 1M scenario - the rate is halved along with the
#                                     count - so it costs the time of the real answer to give
#                                     half of it. It stays in the AWS set, where 1M is not run.
#

#                                     50k/s scenario - see the note in results/Fan-In-local.txt.
