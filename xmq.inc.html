XMQ is a project aiming to create a fast and powerful message queue server. It is aproaching version 1.0. That means that server and test utilities are already working, and you can try them on your system. The server currently supports Linux (.deb and .rpm flavours) and MS Windows (installer isn't yet available). The binary files are availably on Download page, along with SPTK downloads.

At the current stage of development, XMQ server uses 300+ unit tests. If you decide to give it a try, please email any bugs or shortcomings that you discover, and I will do my best to resolve them. For every noticable bug, corresponding unit test is added.

Installation

The current version only supports Linux installation. The Windows version works but needs more testing. The OpenBSD version is being tested.

Linux

The XMQ server installation requires installation of SPTK and XMQ server packages. In SPTK packages, the following packages are required by XMQ:

  • sptk-core

  • sptk-db

  • sptk-db_mysql

  • sptk-db_postgresql

  • sptk-db_sqlite3

  • xmq-server

Download the required packages from http://www.sptk.net (Download page) to an empty directory. Execute the following command (in that directory), depending on the flavor of your Linux:

For Ubuntu, Debian, and Linux Mint

apt install ./*.deb

For Fedora and Oracle Linux:

rpm install ./*.rpm

Configuration

Host Configuration

The host configuration is well described in eMQX performance tuning document: https://docs.emqx.com/en/emqx/latest/performance/tune.html . With the exception to Erlang (that XMQ server isn’t using), all described Linux host adjustments are applicable.

Configuration File

XMQ Server uses single configuration file, xmq_server.conf, located in /etc/xmq directory for *nix and in C:\ProgramData\xmq for Windows. These locations are the default, and can be changed using xmq_server command line --configurtaion-file argument.

The default installation installs a template of this file, xmq_server.conf.template. During the startup, XMQ server tries to open the configuration file, and if it isn't found - tries to create a configuration file from a file with extra ".template" suffix. This is done to prevent overwriting the user-defined configuration during (re)installation of XMQ server.

Having several configuration files may be useful, for instance, if you are intending to run several xmq_server instances on the same host. For this case, it is important to allocate different resources, such as port numbers or persistence databases, for different instances.

The configuration file uses JSON format. XMQ server loads it once upon the start. It is possible to make changes in configuration using XMQ control API described in a separate document.

Connections

XMQ Connection Listeners

Connection listeners are used for accepting client connections. They have no effect on the connection performance after accepting that connection.

XMQ Server allows defining one or more connection listeners. There is no direct limitation on them other than total number of threads and ports on the host. Defining more than one listener per protocol could be useful if you want some load distribution between several XMQ server instances related to connection ports. Typically, the number of listeners is between 4 and 8 per port number.

XMQ listener is defined by a combination of the following parameters:

  • a port number that must be unique upon listeners. The traditional port number is 1883 for MQTT and 8883 for MQTT over SSL.

  • a bind ip address that is 0.0.0.0 by default. It can be set to a local ip address of a network interface. Binding may be useful if a server hosts has several interfaces with different IP addresses.

  • a number of threads accepting the incoming connections. It can be one or more. Setting that number above eight doesn't increase the listener performance in most practical cases, however your results may vary.

  • a protocol that can be ether "tcp" or "ssl". If the requested protocol is "ssl", it's necessary to define valid SSL keys in the "ssl_keys" section of the configuration file.

  • a boolean enable parameter enables or disables a listener.

        • SSL keys

SSL keys are shared by all SSL listeners in the configuration file. They are using PEM format, and consist of CA certificate, server-specific key and certificate, and verify depth. The default SSL keys that come with XMQ server installation are only there for making things work initially. The actual keys that are specific to your server should have different names than installed by XMQ server, and configuration file should be modified accordingly.

Queue Limits

Queue limits define maximum values per queue or topic:

  • max_size is the maximum number of messages stored in the queue or topic befor it's considered full. Any messages arriving to full queue or topic are discarded.

  • max_inflight_messages define maximum number of not yet acknowledge messages with QOS1 or QOS2 that server sends to a client. After reaching this number of messages in the flight, the server will wait until some messages are acknowledged, and then will continue.

Server Limits

Server limits affect the whole server:

  • receive_threads is the number of threads used to receive incoming messages.

  • send_threads is the number of threads used to send outgoing messages.

  • max_topic_alias set the limit of topic aliases per client session.

Authentication

Currently, XMQ only supports password-based authentication. Optionally, the authentication can be switched to anonymous mode. Combining SSL listeners with anonymous mode gives you certificate-based authentication.

XMQ server template configuration comes with two users defined. It's recommended to change these users passwords, and define own users - using xmq_ctl utility. Keeping the user "admin" is necessary for configuration as xmq_ctl uses it.

Persistence

XMQ server supports optional persistent mode. In persistent mode, the incoming QOS1 and QOS2 messages are stored into the database by the topic and client ID, and removed when they are delivered to client. The QOS0 messages are not persistent.

The message persistence means that server may survive the crash or failure with minimum message loss after restart – as far as the persistent storage isn’t affected. The maximum message loss is estimated to a number of messages passed within last 100ms before the crash. The actual result depends on the persistence database performance.

The persistence requires Redis server. If the redis_uri parameter is an empty string, then there is no message persistence. The choice of the database depends on the requirements to the server's performance and reliability.

  • PostgreSQL provides high reliability and medium performance. The persistence database can be located on the same host, or on the different host. This persitent storage is good for most of the use cases.

  • SQLite provides medium reliability and high performance. The reliabilty is limited since SQLite database is running on the same host. Placing it on a network share was not tested.

  • MySQL provides high reliability and low performance. The performance is limited because this version of XMQ server can only use MySQL in a single writer thread.

  • Support for MS SQL and Oracle, as well as for a generic ODBC databases, is possible in the future.

Logging:

Logging is writing internal server events to the log file. Logging defines where is log file stored, logging level, and what details should be logged. The configuration file contains items log_levels_available and log_subjects_available that suggest possible values that can be used in corresponding settings. The log_level expects a single value, while log_subjects expects comma-separated set of values.

  • log_to defines the log file location. Currently, there is no support for log rotation yet.

  • log_level is the minimum log message priority allowed. For instance, with log_level "INFO", logging of "DEBUG" information is not written to the log file.

  • log_level_available lists values that can be used in log_level setting.

  • log_subjects lists log message subjects that are captured to the log file. Messages with different log subjects are not written to the log file.

  • log_subjects_available lists values that can be used in log_subjects setting.

Web Service

Web service is the XMQ server control API. It can be used as XML Web Service or as REST. The only setting available is the listener port number.

Utility Programs

XMQ server comes with a set of command-line utilities that can be used to test and tune XMQ server. The command line options are available if a utility is called with –help option. The utility programs can work with a generic MQTT server.

xmq_conn

Test connecting of one or more clients to the server.

xmq_pub

Send messages to the server using one or more clients.

xmq_sub

Subscribe one or more clients to the topic(s).

xmq_ctl

Administration of XMQ server such as modifying users.
