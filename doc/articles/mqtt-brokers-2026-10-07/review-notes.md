# Проверки перед публикацией

Черновик использует только серию `LoadTest/results/AWS/2026-10-07`. Старые измерения не смешаны с ней. Persistence включён отдельным разделом: режимы snapshot и записи сообщений указаны явно, равные гарантии сохранности не подразумеваются. Отдельный Redis не входит в CPU/RSS XMQ.

Происхождение сценариев добавлено со ссылками на MQTT Benchmark Suite и сравнение EMQX/Mosquitto от 23 апреля 2023 года. Источник сообщает c5.4xlarge, текущая серия — c5n.4xlarge; отличаются генератор, версии, ОС, длительность, P2P rate и число соединений. Не называть текущую серию точным воспроизведением. Утверждение «последняя статья на сайте EMQX» не используется: подтверждена дата выбранной публикации, а не отсутствие более поздних публикаций.

## Вопросы, влияющие на выводы

1. **EMQX fan-in — причина установлена** (журнал EMQX на стенде): EMQX загружен на все 16 ядер и доставляет 1–3,5 тыс./с из 50 тыс.; очереди подписчиков растут, пока процессы не превышают `force_shutdown.max_heap_size` (6291456 слов = 48 МБ, «maximum heap size reached ... Kill: true»), и EMQX закрывает подписчиков. Прогонов с повышенным лимитом НЕ было: автор решил, что смысла нет — скорость доставки это не меняет. Утверждение черновика о «дополнительных проверках» было неверным и удалено. Числа — исходный AWS-прогон: пять непустых интервалов, 484103 доставки из 30 млн.
2. **Метод задержки.** `scenario/RoundTripInterval.cpp`: FIFO sent/received, не message-ID correlation. В fan-in очередь общая. Отброшенные сообщения или дубликаты могут смещать соответствие времён отправки и получения; перемена порядка осложняет интервальные результаты. Нужен контрольный прогон для HiveMQ fan-in (~972 ms постоянно) и EMQX, желательно с корреляцией по идентификатору сообщения и проверкой числа отправленных/полученных/дублированных сообщений. Наблюдение не заменяется утверждением о причине.
3. **Ресурсы.** Заголовок сообщает 40Gb RAM для c5n.4xlarge. Проверить фактическую память через сохранённый `MemTotal` или сведения EC2; число не перенесено в статью. В отчёте клиента сказано 29 bound addresses, в console — 30 local interfaces: уточнить, включает ли второе основной адрес.
4. **Воспроизводимость.** Сохранить полные конфиги пяти брокеров и снимки JSON, команды запуска, точный commit/build-id генератора, сведения о TLS и авторизации, параметры sysctl и ulimit. Путь к `.log` в console относится к AWS-клиенту и не является опубликованной ссылкой. Обеспечить публичный доступ к материалам именно этой серии.
5. **Mosquitto.** В итоговой серии указан `max_inflight_messages=65534`; в первой campaign.sh остался 0, есть отдельная неудачная серия `.quota0`. Для статьи брать только итоговую серию и сохранить фактически применённый конфиг. Настройка для большой нагрузки не доказывает глобальный максимум производительности на всех конфигурациях.
6. **CPU/RSS.** Peak CPU EMQX выше 1600%: проверить метод семплирования и знаменатель, не заявлять «невозможную» загрузку. В fan-out EMQX табличный RSS достигает 638 MB, а отдельный `Max RAM` равен 617 MB: выяснить происхождение расхождения. Таблицы статьи используют отдельные `CPU Load` и `Max RAM`, без смешивания источников.
7. **Прогрев и повторы.** У HiveMQ CE сильный стартовый участок в point-to-point и fan-out. Не удалять его выборочно. Для следующей серии установить общий warm-up и повторить ключевые сценарии; разницу FlashMQ/XMQ в несколько микросекунд не трактовать как статистически подтверждённую.
8. **Предел нагрузки и доставка.** Полученная скорость зависит от очередей, backpressure, завершения сценария и окна учёта. Не приравнивать недоставленные к концу окна сообщения к потерянным. Не утверждать максимальную пропускную способность по одной целевой скорости.

## Уточнение XMQ persistence

Пользователь подтвердил топологию: в AWS Redis локальный; на местном стенде Redis на отдельном хосте, диск не SSD. Местные результаты в статью не включаем. Независимый отказ хоста XMQ при работающем Redis относится к местной топологии, не к AWS-серии.

Пользователь описал окна потери 10 мс при отказе XMQ с работающим Redis и 1 с при отказе Redis в Durable. Код и текущая страница persistence уточняют: 10 мс — write-behind delay, лимит неподтверждённых записей задаётся max_queued_writes (1000 в этой серии). Не заявлять безусловный временной предел без проверки обработки замедленного/недоступного Redis. AOF everysec описывать как обычное окно синхронизации, разделять Redis process crash и Redis host/power failure. В AWS-отчёте Redis локальный; отдельный хост Redis — другая топология.
