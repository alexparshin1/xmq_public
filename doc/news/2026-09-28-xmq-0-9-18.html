XMQ 0.9.18 is out. It is mostly about doing everything faster. You can download it here.

The whole machine, not half of it

The --no-cpu-affinity option is replaced with --use-cpu-affinity. Affinity is now off by default.

The broker used to pin itself to one hardware thread per physical core and leave the hyperthread siblings unused. On our test bench that cap was the whole of a latency cliff: Point-To-Point held under a millisecond at 100,000 messages a second and jumped to 158 ms at 125,000, while five of the eight CPUs sat idle. With pinning off by default, the same runs go 125,000 a second comfortably and 150,000 well — within 3% of FlashMQ on the same client and scenario. --use-cpu-affinity turns pinning back on for anyone who wants it.

Use less memory

The message path lost half its allocations — about six per message fewer — by not building a heap copy of a callback on every subscription lookup and by reusing the list of recipients from one message to the next.

How much is waiting

The counters always said what the broker had done. Now it also reports how much work is queued in each of its three stages — receiving, delivering and sending — once a second, on $SYS/broker/queues/…/length, in the statistics API, and in a new Queues panel on the dashboard. A queue that keeps growing is a broker falling behind, and that is now visible before it becomes latency.

Smaller things worth knowing

  • The log says which signal stopped the broker. A clean stop with no reason beside it used to read as the broker deciding to quit.
  • The load client warns when its source addresses are on a VPN tunnel — such a run measures the tunnel, not the broker.
  • The configuration interface runs on one worker thread instead of four; nothing it serves needs more.
