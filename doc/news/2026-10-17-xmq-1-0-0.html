XMQ 1.0.0 is out. It is the first release under a compatibility promise: the extension ABI, the configuration keys and the control API stay as they are through 1.x. You can download it here.

Clustering

This is the release that makes XMQ a cluster. Nodes share one Redis store and one accounts database, and a client may connect to any of them: the node it reaches takes its session, with its subscriptions and queued messages, wherever that session was before. Which node answered a client is no longer something the client, or its session, has to remember.

A cluster has a coordinator, and each node holds a lease in Redis. When a node dies, its lease expires, the survivors adopt its sessions and keep collecting for them, and a client that comes back anywhere finds its session again. When the coordinator itself goes, the next node in the order takes over in a new term. Cluster links are MQTT over TLS, and a cluster admits up to ten nodes.

We measured it on four AWS c5n.2xlarge nodes and a single client, against EMQX 5.8.9, the last Apache-licensed release that clusters. XMQ held 500,000 connections at 542 µs median connect latency (EMQX 1,717 µs), a 50,000-publisher fan-in at 426 µs (1,027 µs), a 250,000-delivery fan-out at 1,239 µs (1,661 µs), and 100,000 point-to-point messages a second at 489 µs (892 µs). The four-node cluster results have the method and the charts.

Throughput is only half of it. In the survivability run, each node was killed outright with kill -9 and left down for 20 seconds while the cluster carried traffic: 45 of 45 checks passed, the survivors kept serving and delivering, and every node carried traffic again after it came back. The throughput scenarios use clean sessions and do not exercise session state; a separate persistent-session check moved 10,000 queued QoS 1 messages from a killed node to another with no loss.

Persistence that holds when the disk is slow

Two changes, one problem. The broker looked a connecting client's stored session up with a request that held a thread until Redis answered: with Redis syncing every write (appendfsync always) on a USB hard disk, 0.9.19 refused 32,000 of 40,000 connections. The lookup is asynchronous now and CONNECT completes when the answer comes - no refusals on the same disk.

And a message's persistence record waits 10 ms before it is written, and is never written at all if the message has been acknowledged by then. On that same disk, with every write synced: 40,000 persistent messages a second at 159 µs. 0.9.19 managed 1,500 a second.

TLS at the front

The thread counts behind auto are four send, six receive and four delivery. Decryption happens on the receive path, and the old counts - read from the core count - left point-to-point over TLS at 100,000 messages a second at 549 µs; at the new ones it is 273 µs, against FlashMQ's 254 µs. The trade is deliberate and not free: the plain-text scenarios give back 3 to 18 per cent.

Fixed

  • On Windows a client that failed the TLS handshake could bring the broker down - a port scanner on the TLS port was enough. The accepted socket was closed twice, the second time in a way meant for files; it is closed once now, on every platform.
  • MQTT client shutdown could clear a callback while it was running, or destroy the client before its receiver returned - a crash during reconnects and bridge rebuilds.

Smaller things worth knowing

  • xmq_server --set-password asks for the password at a terminal and does not echo it. From a pipe it reads standard input as before.
  • RPM packages install beside the standalone SPTK packages without conflicting .build-id links.
  • The Docker image no longer sets the administrator's password from XMQ_ADMIN_PASSWORD: it reset the password on every start and showed it in docker inspect. Set it once with xmq_server --set-password admin inside the container and keep /etc/xmq in a volume. A container that relied on the variable and kept no volume has no administrator password after the upgrade.
