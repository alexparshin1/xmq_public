XMQ 1.1.0 is out. It opens the broker outwards: what it accepts, and what it could not do, can now reach an HTTP(S) endpoint - with a payload you choose, with a signature the receiver can verify. You can download it here.

  • A webhook extension posts accepted messages to HTTP(S). It listens on the message tap with a topic filter and sends JSON with the payload in base64, so a binary message survives the trip. A configured secret signs the exact body with HMAC-SHA256 in X-XMQ-Signature, failed requests are retried with backoff, and a bounded queue means a slow endpoint costs deliveries, never publishing throughput.
  • The broker's own log is a second input. sources picks messages, log records, or both, and log_min_level with log_subjects narrows the log. These are the records that explain why a message never existed at all: refused connections, denied permissions and extension faults.
  • Your payload, your headers. The default payload is three fields - {"topic":"{{topic}}","message":"{{message}}","level":"{{level}}"} - and template replaces it with any JSON, substituting {{topic}}, {{message}}, {{level}} and the other names with JSON-escaped values. headers adds request headers such as an authorization token, one Name: value per item; where several receivers are wanted, a web server in front of one endpoint fans the stream out.
  • One endpoint can watch several topic filters. topic_filter is a list: the Extensions page shows one field per filter with Add and Remove, and a message matching any of them is sent. The broker registers the tap with those filters rather than with #, so a topic nobody wants costs one comparison and not a copy of its body.

The Data Integration page has the settings, the request format, the signature and what the connector costs a busy broker.
