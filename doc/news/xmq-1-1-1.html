XMQ 1.1.1 brings metrics, structured logs and health checks together so you can see how your broker is behaving - and what needs attention - before clients report a problem. You can download it here.

  • Scrape broker and host metrics with Prometheus. A dedicated, optional HTTP endpoint reports connections, message traffic, queue depths, storage, cluster topology, and CPU and memory usage. Configure the listener and optional HTTP Basic authentication from the management interface without restarting MQTT.
  • Distinguish a running process from an online broker. The metrics listener provides /healthz for liveness and /readyz for readiness, reflecting whether MQTT is serving clients, including whether a cluster node holds its lease, so a load balancer or Kubernetes probe can stop routing clients to a node that is not ready.
  • Search structured logs by node and event. Optional JSON output gives each log record a timestamp, level, node, subject or component, and message, ready for collection from a file or container stdout. Plain-text logging remains the default.
  • Go from metrics to logs in one monitoring stack. A ready-to-run Docker Compose example connects XMQ, Prometheus, Grafana, Loki and Grafana Alloy with provisioned dashboards and alert rules. Start exploring broker metrics and the corresponding logs without assembling the monitoring stack from scratch.
  • Make persistence backpressure and broken cluster links visible. Dedicated metrics show publishers paused while storage catches up, registered cluster nodes, connected peers and outgoing links. Dashboards and alert rules highlight sustained publisher pauses and missing peer links, rather than leaving you to infer them from falling throughput.

The Prometheus endpoint is off by default and reports each node separately; Prometheus provides history and Grafana provides dashboards and alert delivery. See the Prometheus guide for configuration, metric definitions and the Docker observability stack.
