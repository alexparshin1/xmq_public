XMQ now lets you choose the persistence behavior from the management interface. Both modes store persistent sessions, subscriptions, retained messages and undelivered QoS 1 and QoS 2 messages in Redis. They differ in when a publish is acknowledged and how Redis writes reach disk. See the new Persistence guide for the guarantees and failure boundaries.

Persistent: keep the write-behind path

Persistent mode keeps the 10 ms write-behind behavior and disables Redis AOF to avoid its additional write latency. Max queued writes defaults to 1000; when that queue fills, publishers pause until Redis catches up. A publisher may be acknowledged before Redis stores the record, and recovery after a Redis restart depends on RDB snapshots.

Durable: wait for Redis to sync each write batch

Durable mode enables Redis AOF with appendfsync always. XMQ waits for Redis to confirm a local AOF fsync before sending successful publish acknowledgements. This protects acknowledged writes against an ordinary Redis process restart while its disk remains intact; loss of the Redis host or disk is outside this guarantee.

Switch from the interface

Choose Persistent or Durable on the Persistence screen and apply the change. XMQ checks and updates Redis configuration, saves it, then restarts the MQTT service; Redis itself does not restart. The configuration change affects the entire Redis server and every database and application using it, so a dedicated Redis instance is recommended when other workloads need different settings. The accepted Point-To-Point-60K-persistence performance test found no performance regression in the tested configuration.
