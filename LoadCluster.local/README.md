# xmq_scn_cluster — как это работает

## Зачем он нужен

`xmq_scn` прогоняет сценарий и на этом заканчивается: сценарий стартовал, отработал, завершился.
Кластер проверяется обратным — узлом, снятым посреди нагрузки, узлом, вернувшимся в кластер,
который без него успел уехать, потерянным и найденным хранилищем. Записать это сценарием нельзя:
сценарий не умеет останавливать брокера.

Поэтому тест — это два потока работы, идущих одновременно:

- **нагрузка** — обычный сценарий `xmq_scn` (файл из `LoadTest/Cluster/`), запущенный ровно так,
  как его запускает `xmq_scn`, но в отдельном потоке;
- **таймлайн** — список моментов, в которые процесс останавливает узел, поднимает его или смотрит,
  что кластер о себе думает.

После этого — **проверки**: они и решают, прошёл тест или нет. Первый и последний шаг (нагрузку)
пишет сценарий, всё остальное описывает файл теста.

## Как идёт прогон (порядок, который важно помнить)

```
t = 0            старт нагрузки (поток), от этого момента считаются все "at" таймлайна
t = as задано    шаги таймлайна в основном потоке: stop / start / check
                 каждая команда узла выполняется через shell, где {node} — имя узла
конец нагрузки   поток нагрузки завершается сам (сценарий доигран)
потом            оставшиеся проверки и итоговая таблица
```

Отсчёт — от старта нагрузки, а не от предыдущего шага: `"at": 60` — это «на 60-й секунде нагрузки»,
и порядок шагов в файле на это не влияет (файл можно группировать как удобно, шаги сортируются).

Вывод: строки нагрузки (таблицы `xmq_scn`) и строки таймлайна идут в общий поток, каждая со своим
штампом `+NN.Ns`, поэтому в логе видно, кто в какой момент что сделал.

## Формат файла теста

```json
{
  "name": "the second node is taken away and brought back under load",
  "server": { "username": "user", "password": "User-Secret1" },
  "load": {
    "scenario": "cluster-p2p-small.json",
    "groups": [ { "name": "publishers", "node": "node1" },
                { "name": "subscribers", "node": "node2" } ]
  },
  "nodes": [
    { "name": "node1", "host": "thinker11", "port": 2884,
      "stop":  "ssh thinker11 /home/alexeyp/cluster/stand.sh stop {node}",
      "start": "ssh thinker11 /home/alexeyp/cluster/stand.sh start {node}" },
    { "name": "node2", "host": "thinker11", "port": 2885,
      "stop":  "ssh thinker11 /home/alexeyp/cluster/stand.sh stop {node}",
      "start": "ssh thinker11 /home/alexeyp/cluster/stand.sh start {node}" }
  ],
  "timeline": [
    { "at": 30, "action": "stop",  "node": "node2" },
    { "at": 60, "action": "start", "node": "node2" },
    { "at": 100, "action": "check" }
  ],
  "checks": [ ... ]
}
```

| поле | смысл |
|---|---|
| `name` | имя теста для отчёта |
| `server` | аккаунт кластера и адрес по умолчанию для того, что не назвало своё |
| `load.scenario` | имя файла сценария нагрузки; относительный путь ищется рядом с файлом теста |
| `load.groups[]` | какой узел обслуживает группу нагрузки: `name` (`publishers` или `subscribers`) и `node` |
| `nodes[]` | узлы: `name`, `host`, `port`, `stop`, `start` |
| `timeline[]` | `at` (секунды от старта нагрузки), `action`: `stop` \| `start` \| `check`, `node`, `check` |
| `checks[]` | что должно быть верно; см. ниже |

**Адрес узла живёт в узле и только там.** Проверка пишет `"node": "node2"`, группа нагрузки —
`"node": "node1"`, и порт не повторяется ни в проверках, ни в сценарии: инструмент подставляет
адрес узла и в нагрузку, и в проверки. Перенести тест на другой стенд — это правка `host`/`port`
у узлов и ничего больше. Группа, не названная в `load.groups`, остаётся там, куда её послал
сценарий.

Команды `stop`/`start` — обычные команды оболочки, потому что инструмент не владеет узлами: на
стенде это процессы и `stand.sh`, на ферме — служба, в контейнере — что-то третье. Разное только
написано в файле теста, остальное одинаково. `{node}` подставляет имя узла, так что команда
пишется один раз на все узлы. Если команда вернула не ноль — **тест падает**, даже если все
проверки прошли: иначе проверки подтверждали бы кластер, с которым ничего не сделали.

## Проверки

Четыре вида. Первый смотрит в общее хранилище (что кластер думает о себе), остальные — глазами
клиента (что видит клиент). Смысл теста — что эти две картины сходятся.

**`redis`** — запрос в Redis, ответ сравнивается:

```json
{ "name": "both nodes are members", "kind": "redis",
  "uri": "redis://thinker11:6379/4", "command": "ZCARD cluster:members", "expect": "2" }
```

Ожидание ровно одно из: `expect` (ответ целиком), `contains` (часть ответа), `min` (ответ как
число не меньше), `nonempty`, `empty`. Команда пишется как строка: слова разделяются пробелами,
кавычек нет — если ответ возвращает несколько значений, они склеиваются через запятую, поэтому
для счёта берут `ZCARD`/`LLEN`, а не `KEYS`.

**`connect`** — клиент доходит до узла (или не доходит):

```json
{ "name": "the node that was away serves clients again", "kind": "mqtt", "action": "connect",
  "node": "node2", "expect": true }
```

`expect: false` — проверка на отказ, например «клиент с чужим session id не пускается».

**`deliver`** — сообщение доходит между узлами: публикуется на одном, принимается на другом:

```json
{ "name": "a message crosses the cluster", "kind": "mqtt", "action": "deliver",
  "publish-node": "node1", "subscribe-node": "node2",
  "topic": "cluster/test/cross", "payload": "cross-node", "timeout": 15 }
```

**`retained`** — то же, но retained: публикуется до подписки, читается тем, кто подключился позже
(в конце проверка подчищает топик, чтобы следующий прогон не прошёл по чужому следу).

Вместо `node` / `publish-node` / `subscribe-node` можно назвать адрес напрямую (`host`/`port`,
`publish-host`/`publish-port`, `subscribe-host`/`subscribe-port`) — это нужно, когда проверка
смотрит не на узел кластера, а на что-то другое. Узел имеет приоритет: если названо и то и другое,
проверка пойдёт на узел.

Проверки чёрного ящика соединяются **MQTT 5**, если не задан `-V`: кластер — это территория 5
(session takeover, reason codes, retained), и проверка должна видеть то, что видит клиент кластера.

## Ключевые опции

| опция | зачем |
|---|---|
| `--scenario, -s <file>` | файл теста (обязателен) |
| `--dry-run` | разобрать файл, напечатать план и проверки — и выйти, ничего не запуская |
| `--load-scenario <file>` | подменить сценарий нагрузки, оставив ту же топологию и таймлайн |
| `--host/--port/--username/--password` | перекрыть сервер из файла теста (проверки и нагрузка) |
| `-I, --bind-to-interfaces` | разложить клиентов нагрузки по локальным адресам (как в `xmq_scn`) |
| `--connect-intervals`, `--result-interval` | сколько строк в фазах подключения и публикации |
| `-k, --keep-alive`, `-V`, `--cafile` и т.д. | базовые опции `xmq_scn`, действуют на нагрузку и на проверки |

Код возврата: `0` — все проверки прошли и все шаги таймлайна выполнились, `1` — иначе. Печатается
таблица: что проверялось, что ожидалось и что нашлось.

## Как запускать

```bash
# сборка (уже собрано; после правок кода — повторить)
cd ~/build/xmq_cluster_client && make -j8 xmq_scn_cluster

# посмотреть, что тест сделает
~/build/xmq_cluster_client/utilities/xmq_scn_cluster \
  --scenario ~/workspace/xmq_public/LoadCluster.local/the-second-node-comes-back.json --dry-run

# прогон (нагрузка 150 с + проверки)
~/build/xmq_cluster_client/utilities/xmq_scn_cluster \
  --scenario ~/workspace/xmq_public/LoadCluster.local/the-second-node-comes-back.json
```

Стенд: `~/cluster/stand.sh up|down|start|stop|status|wipe|tail <узел>` — лежит на каждой машине,
которую использует, и запускается с любой из них.

## Стенд на нескольких машинах

Узел записывается как `имя@машина`, и стенд умеет поднять кластер сразу на нескольких машинах —
межузловые линки тогда идут через настоящую сеть, а не через loopback:

```bash
NODES="node1@thinker10 node2@thinker10 node3@thinker11 node4@thinker11 node5@theater node6@theater"
```

Это и есть раскладка по умолчанию: по два узла на thinker10, thinker11 и theater. Порты считаются
от номера узла и уникальны по всему стенду, поэтому два узла на одной машине не сталкиваются:

| узел | машина | клиентский | TLS | web |
|---|---|---|---|---|
| node1 | thinker10 | 2884 | 9883 | 28883 |
| node2 | thinker10 | 2885 | 9884 | 28884 |
| node3 | thinker11 | 2886 | 9885 | 28885 |
| node4 | thinker11 | 2887 | 9886 | 28886 |
| node5 | theater | 2888 | 9887 | 28887 |
| node6 | theater | 2889 | 9888 | 28888 |

Что на каждой машине (одинаковые пути на всех, поэтому конфигурация узла переезжает без правок):

- `~/cluster/xmq_server` — сборка из текущей ветки, своя на каждой машине;
- `~/cluster/lib/libxmq_user_database.so` — расширение аккаунтов;
- `~/cluster/stand.sh` и `redis_query.py`;
- каталог узла `~/cluster/<узел>` — конфиг, ключ, сертификат, логи, pid-файл.

Что общее для всего стенда:

- **Redis на theater, база 4** — единственный арбитр кластера. Строка `redis_uri` обязана
  совпадать у всех узлов (кластер сравнивает её как строку), поэтому ни прокси, ни своё хранилище
  отдельному узлу дать нельзя;
- **PostgreSQL на theater** (`postgresql://xmq:xmq_secret@theater/xmq`) — одна база аккаунтов на
  весь кластер; без неё узлы не аутентифицируют даже друг друга;
- **CA стенда** — создаётся там, где запускают `stand.sh`, а на узлы уезжают только их сертификаты
  (приватный ключ CA остаётся на месте запуска).

Подготовка машины к участию в стенде (делается один раз на машину):

```bash
# сборка из текущей ветки; на машинах, где SPTK не 5.6.14, — своя копия SPTK рядом
cmake -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=$HOME/cluster/install \
      -DSPTK_INCLUDE_DIR=$HOME/sptk/include \
      -DSPTK_LIBRARY_CORE=$HOME/sptk/lib/libsputil5.so \
      -DSPTK_LIBRARY_SPDB=$HOME/sptk/lib/libspdb5.so \
      -DSPTK_LIBRARY_WSDL=$HOME/sptk/lib/libspwsdl5.so <исходники> && make -j8 install
cp <сборка>/xmq_server ~/cluster/xmq_server
cp $HOME/cluster/install/lib/xmq-extensions/libxmq_user_database.so ~/cluster/lib/
```

Расширение собирается шагом `make install` (отдельная цель `xmq_user_database` линкует библиотеку,
но не кладёт её в дерево сборки — её место задаёт установка), поэтому в дереве сборки его искать
бесполезно.

| `cluster-p2p-small.json` | сама нагрузка: 200 издателей и 200 подписчиков, 150 с; какой узел обслуживает группу, говорит файл теста |

## Что инструмент пока не умеет

- **Одна нагрузка на тест.** Сценарий не может разложить группу клиентов на два сервера, поэтому
  «половина клиентов на каждом узле» выражается только двумя нагрузками сразу — этого в раннере
  ещё нет. Из-за этого снятие узла с измеряемыми клиентами останавливает доставку: публикация
  идёт до конца окна, а таблица доставки перестаёт расти (проверено).
- **Команды узлов выполняются там, где запущен инструмент.** Для прогона с клиентской машины они
  пишутся как `ssh thinker11 …` — это дело файла теста.
- **Redis-проверка — один запрос и одно ожидание.** Составных проверок («и то, и это») нет.
